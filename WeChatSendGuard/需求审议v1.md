# 一、最需要修改的地方：FR-05 的“聊天窗口标题 = 聊天对象名称”

这是整份文档最大的风险。

> `GetForegroundWindow()` → `GetWindowText()` → 得到聊天对象名称 → 和群名名单比较

文档中明确把它作为 MVP 的 P0 核心方案。

甚至代码已经写成：

```csharp
IntPtr chatWnd = GetForegroundWindow();
StringBuilder title = new StringBuilder(256);
GetWindowText(chatWnd, title, 256);
string chatName = title.ToString();

bool isGroup = groupList.Any(
    g => chatName.Contains(g, StringComparison.OrdinalIgnoreCase)
);
```



### 这里有一个非常关键的问题

**必须先验证：你当前目标微信版本中，真正拥有“当前聊天名称”的窗口到底是哪一个。**

不能从：

> “微信界面顶部显示群名称”

直接推导：

> “这个字符串就是 GetWindowText(GetForegroundWindow()) 返回的标题”。

这是两个不同层面的东西。

尤其你后面又写了：

> 微信主窗口类名 `WeChatMainWndForPC`
> 微信聊天窗口类名 `ChatWnd`



这里其实已经暴露出一个架构问题：

### 你现在需要先搞清楚微信到底是什么窗口结构

建议技术预研第一步不是写 WPF，而是做一个：

**WeChat Window Inspector**


所以建议设计一个明确的状态机。

# 四、建议增加一个“Overlay State”

我认为这是当前文档最应该补的一块。

例如：

```text
NONE
 ↓
WECHAT_NOT_FOUND
 ↓
WECHAT_MINIMIZED
 ↓
WECHAT_INACTIVE
 ↓
CHAT_UNKNOWN
 ↓
PRIVATE_CHAT
 ↓
RISK_GROUP
```

对应覆盖层：

| 状态     | 覆盖层     |
| ------ | ------- |
| 微信不存在  | 隐藏      |
| 微信最小化  | 隐藏      |

```text

```

这反而会产生**错误安全感**。

所以应该采用：

> **无法确认 ≠ 私聊**

所以我不会建议你现在直接开始写完整程序。

**最合理的下一步是先做一个非常小的“微信窗口侦察 Demo”。**

它甚至不需要 WPF UI，只需要启动后输出：

```text
HWND
ProcessId
ClassName
WindowText
Parent
Owner
Rect
Foreground
Visible
```

然后你分别操作：

```text
① 微信主界面
② 私聊
③ 群聊
④ 切换私聊 → 群聊
⑤ 移动微信
⑥ 最大化
⑦ 最小化
⑧ 切换到 Chrome
```

把日志拿出来，我们就能先把**“到底哪个窗口代表当前聊天、标题到底能不能拿到群名”**这个最大的未知数解决掉。

**这个验证一旦通过，你这份需求文档大约 80% 就可以直接进入编码；如果验证不通过，则应该先改 FR-01/FR-05，而不是继续堆 Overlay 代码。**
