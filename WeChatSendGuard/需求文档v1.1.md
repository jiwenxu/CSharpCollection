## 1. 项目背景与目标

### 1.1 背景
PC 端微信中，群聊与私聊的聊天窗口视觉结构高度相似。用户打字时视线聚焦在底部输入框附近，最多扫到相邻几条消息，难以注意到顶部聊天名称。手快时容易把私密内容误发到**高风险的聊天对象**（常见为群聊），造成尴尬甚至严重后果。

### 1.2 目标
开发一个轻量级 Windows 辅助工具，在微信聊天窗口上方叠加一个**独立、透明、不干扰操作**的提醒层。当当前聊天对象命中用户维护的**高风险聊天名单**时，通过醒目的视觉元素（红色边框、标签、文字）进行强提醒，降低误发概率。

### 1.3 范围
- **包含**：窗口发现、聊天对象识别（MVP 采用手动名单）、风险匹配、透明覆盖层绘制与同步、配置界面、开关控制、失败兜底策略。
- **不包含**：修改微信客户端、拦截消息发送、读取聊天内容、监听键盘、自动判断所有群聊（见第 12 节版本演进）。

### 1.4 设计原则
1. **无法确认 ≠ 安全**：识别失败时不得给出"安全/私聊"的暗示。
2. **零干扰优先**：覆盖层在任何情况下都不得抢焦点、遮挡输入或吞掉鼠标事件。
3. **识别逻辑可替换**：识别方式（`GetWindowText` / UI Automation / 其他）必须可独立替换，覆盖层不受影响。
4. **先验证后编码**：核心未知项（第 7 节）未验证前，不进入核心开发。

## 2. 需求概述

### 2.1 用户故事
> 作为一个经常在 PC 微信上聊天的用户，我希望在打开一个高风险聊天窗口时，能立刻看到明显的提醒标识，这样我就不会把私密内容错发过去。

### 2.2 核心需求
1. **实时跟随**：覆盖层始终贴合微信聊天窗口的位置和大小。
2. **风险识别**：判断当前聊天对象是否命中用户配置的高风险聊天名单（MVP：名单匹配）。
3. **强视觉提醒**：命中时显示醒目的边框、标签或文字。
4. **零干扰**：覆盖层不遮挡输入、不抢焦点、可鼠标穿透。
5. **可配置**：用户可管理名单与匹配模式、调整提醒样式、一键开关。
6. **状态安全**：任何识别不确定或异常场景，均不产生"错误安全感"。

## 3. 术语与概念模型

### 3.1 四层概念模型
审议指出 v1.0 把"找到聊天窗口"与"知道当前聊天是谁"混为一谈，v1.1 明确拆分为四层：

```text
微信进程 (WeChat.exe)
   ↓
微信主窗口 (MainWindow, 由类名/进程定位)
   ↓
聊天上下文 (ChatContext: 聊天窗口 Rect + 聊天对象名称)
   ↓
风险状态 (RiskState: 命中 / 未命中 / 无法判定)
```

覆盖层只消费最终状态，绝不直接调用 Win32 API 取窗口信息。

### 3.2 统一状态对象 ChatContext

```csharp
/// <summary>聊天上下文：覆盖层与风险匹配共同消费的唯一状态来源</summary>
public sealed record ChatContext
{
    /// <summary>聊天窗口句柄；无法确定时为 IntPtr.Zero</summary>
    public IntPtr Hwnd { get; init; }

    /// <summary>聊天窗口屏幕矩形（物理像素）</summary>
    public Rect Rect { get; init; }

    /// <summary>当前聊天对象名称；无法确定时为 null</summary>
    public string? ChatName { get; init; }

    /// <summary>聊天对象识别状态</summary>
    public ChatIdentityState Identity { get; init; }
}

/// <summary>聊天对象识别状态</summary>
public enum ChatIdentityState
{
    Unknown,   // 无法判定（读取失败/版本不匹配/切换中）
    Known      // 已取得可用名称
}

/// <summary>风险匹配结果</summary>
public enum RiskState
{
    Unknown,   // 无法判定 —— 不得显示"安全"
    Normal,    // 明确未命中名单
    Risk       // 明确命中名单
}
```

> 说明：`ChatIdentityState` 只回答"是否拿到了名称"，`RiskState` 才回答"是否命中风险"。二者分离，避免"读取失败"被误判为"未命中"。

### 3.3 术语表

| 术语 | 含义 |
|------|------|
| 风险聊天（RiskChat） | 命中用户配置名单的聊天对象；v1.0 中主要体现为高危群聊 |
| 聊天对象名称（ChatName） | 微信聊天窗口当前对应的联系人/群名称 |
| 覆盖层（Overlay） | 本工具的透明、穿透、无焦点独立窗口 |
| 识别链路 | 从微信窗口定位到获得 ChatName 的完整过程 |

### 4.1 FR-05 聊天上下文获取（修订重点）

v1.0 将 `GetForegroundWindow() → GetWindowText()` 直接作为 MVP 既定方案，v1.1 改为**分层、可替换、待验证**：

- **定位**：先定位微信主窗口（特征：进程名 + 窗口类名，类名以第 7 节验证结果为准）。
- **取上下文**：在微信主窗口范围内确定"聊天区域窗口"及其 `Rect`。
- **取名称**：从识别通道取得 `ChatName`。候选通道及实测结果：
  1. ~~窗口标题（`GetWindowText`）~~ —— **实测不成立**；
  2. ~~UI Automation（读取会话标题控件）~~ —— **实测不成立**（微信 4.x 不暴露自动化元素）；
  3. **✅ 视觉 / OCR（Spike-05 验证成立，选定方案）**：对渲染子窗口客户区按 96 DPI 基准偏移区域 `(300,33,580,30)` **经 `dpi/96` 归一化后**裁剪（区域 × `dpi/96`，随后先缩回 96 DPI 基准尺寸、再按整数倍数放大），经三路预处理变体（原色 / 灰度对比拉伸 / 大津二值化）分别 OCR 后取并集，得到当前会话名。
- **抽象**：以上封装为 `IChatTracker`，覆盖层与匹配逻辑只消费其输出的 `ChatContext`。

> **约束**：`GetForegroundWindow()` 不得作为唯一状态来源。前台窗口非微信时应判定为 `WECHAT_INACTIVE`，而非把前台窗口标题当作聊天名。

> **实测结论（2026-09-28）**：窗口标题通道与 UI Automation 通道**均已判定不可用**（详见 7.6）；**视觉 / OCR 通道经验证成立**（详见 7.7，G0/G1/G2 通过、G3 不通过）。FR-05 据此按视觉识别实现编码。
>
> **FR-05 的能力边界（重要）**：
> - 只产出 `ChatName` 字符串，**不产出 `ChatId`、不产出可靠的群/私类型**（G3 不通过），FR-06 不得依赖 `IsGroup` 做判定；
> - 识别结果是**弱信号**，可能为空或误识，必须按"漏报优先于误报"处理（识别失败/为空时不得静默放过，见 FR-09）；
> - `raw` 单路会把拉丁字母误识（`BUG`→`BIJG`），**三路并集是实现约束，不是可选优化**；
> - **裁剪区与放大倍数必须按 `dpi/96` 归一化**（`等效放大 = ocrScale × dpi/96` 须恒定），不得使用固定物理像素偏移 —— 实测固定偏移在 125% 下完全失效。实现上须**先把物理裁剪图缩回 96 DPI 基准尺寸、再按整数 `ocrScale` 放大**：直接按 `ocrScale ÷ (dpi/96)` 放大时 150% 的倍数为非整数 `3.33`，最近邻插值会畸变字形（实测漏报，见 7.7 / Spike-05 第 12.4.3 节）。

### 4.2 FR-06 风险匹配（修订重点）

- 用户维护"高风险聊天名单"，每条支持独立匹配模式：

```json
{
  "matching": {
    "defaultMode": "Contains",
    "caseSensitive": false
  },
  "riskChats": [
    { "name": "技术交流群",     "mode": "Exact" },
    { "name": "产品评审",       "mode": "Contains" },
    { "name": "^项目-.*-2026$", "mode": "Regex" }
  ]
}
```

| 模式 | 语义 | 示例 |
|------|------|------|
| Exact | 完全相等 | 仅命中"技术交流群" |
| Contains | 包含子串 | 命中"技术交流群2""技术交流群（新）" |
| Regex | 正则匹配 | 需转义与容错处理，无效正则回退为 Contains 并告警 |

- 输入 `ChatName == null` 时，输出 `RiskState.Unknown`，**绝不输出 `Normal`**。

### 4.3 FR-07 覆盖层状态机（新增）

v1.0 仅以 `isGroup` 布尔值驱动覆盖层，无法覆盖最小化、失焦、切换中、识别异常等场景。v1.1 引入显式状态机：

```text
NONE
 ↓
WECHAT_NOT_FOUND     微信进程不存在 / 主窗口已关闭
 ↓
WECHAT_MINIMIZED     微信存在但已最小化
 ↓
WECHAT_INACTIVE      微信存在但非前台窗口
 ↓
CHAT_UNKNOWN         微信前台，但聊天对象无法确定（Identity=Unknown）
 ↓
NORMAL_CHAT          聊天对象已确定，未命中名单
 ↓
RISK_CHAT            聊天对象已确定，命中名单
```

| 状态 | 触发条件 | 覆盖层行为 |
|------|----------|-----------|
| WECHAT_NOT_FOUND | 进程/主窗口不存在 | 隐藏 |
| WECHAT_MINIMIZED | 微信最小化 | 隐藏 |
| WECHAT_INACTIVE | 微信非前台 | 隐藏 |
| CHAT_UNKNOWN | 前台为微信但名称无法确定 | 隐藏（默认）；可选灰色"无法识别"提示（默认关闭），并记录日志 |
| NORMAL_CHAT | 已确定且未命中 | 隐藏 |
| RISK_CHAT | 已确定且命中 | 显示红框 + 风险标签 |
| （异常） | 识别链路抛错/超时 | 按 CHAT_UNKNOWN 处理，**不显示危险提示亦不显示安全提示** |

**关键约束**：
1. 状态机输入只能是 `ChatContext` + `RiskState`，禁止各模块自取窗口信息。
2. 进入 `CHAT_UNKNOWN` / 异常状态时，不得回退为 `NORMAL_CHAT`。
3. 状态切换需可观测（日志），便于排查误判。

### 4.4 FR-08 风险强提醒样式

- **边框**：聊天窗口四周 4px 红色/橙色边框。
- **标签**：窗口顶部或输入框上方悬浮显示"⚠️ 风险聊天：XXX"。
- **闪烁**：可选，首次进入风险聊天时边框闪烁 2 次。
- **透明度**：可调，默认 0.85，醒目但不完全遮挡。
- **交互隔离**：视觉层与交互层彻底分离。v1 覆盖层为 **100% Click Through**；若后续需"点击标签打开设置"，另建第二个交互窗口，不改变覆盖层穿透属性。

### 4.5 FR-09 失败策略（新增）

| 失败场景 | 处理 |
|----------|------|
| 微信版本变化导致特征失效 | `ChatIdentityState.Unknown` → `CHAT_UNKNOWN` → 隐藏 + 日志告警 |
| 窗口标题读取失败 | 同上 |
| UI Automation 失败/超时 | 同上 |
| 微信正在切换聊天（瞬时） | 保持上一有效状态至多 N ms（去抖），超时则转 `CHAT_UNKNOWN` |
| 匹配正则非法 | 回退 Contains，记录告警 |

> 设计要点：安全提醒类工具的最大风险不是"漏报一次"，而是**给出错误安全感**。因此一切不确定场景一律表现为"不确定"，而非"安全"。

### 5.1 性能指标（修订：可测量口径）

### 6.3 关键技术点

#### 6.3.1 透明覆盖层窗口（WPF）
```csharp
// 窗口样式
WindowStyle = WindowStyle.None;
AllowsTransparency = true;
Background = Brushes.Transparent;
ShowInTaskbar = false;

// Win32 扩展样式
var hwnd = new WindowInteropHelper(this).Handle;
int exStyle = GetWindowLong(hwnd, GWL_EXSTYLE);
SetWindowLong(hwnd, GWL_EXSTYLE, exStyle | WS_EX_LAYERED | WS_EX_TRANSPARENT
                                        | WS_EX_TOOLWINDOW | WS_EX_NOACTIVATE);
```

> **注意**：`WS_EX_TRANSPARENT` 与"鼠标穿透"并非绝对等价，其真实效果必须通过第 7 节 Spike-02 的**实际点击测试**验证，不得仅凭 API 名称判断。

#### 6.3.2 覆盖层 Z-Order（修订）
- v1.0 的 `Topmost = true` 会导致覆盖层越到记事本/浏览器/IDE/远程桌面等所有普通窗口之上。
- v1.1 目标改为：**覆盖层仅在微信处于目标状态（前台且可见）时显示，并保持位于微信窗口之上；微信失去前台后立即隐藏。**
- 是否使用 `Topmost` 由 Spike-02 结论决定；若使用，必须同时满足"微信失焦即隐藏"。

#### 6.3.3 窗口位置跟踪（修订：分版实施）
- **第一版（MVP）**：50~100ms Timer → `GetWindowRect` → 与上次 `Rect` 比较 → 有变化才 `SetWindowPos`。
  - 100ms 轮询 = 10 次/秒，对桌面辅助程序开销极小，可先满足"延迟 < 100ms / CPU < 1%"。
- **第二版（优化）**：以 `SetWinEventHook`（`EVENT_OBJECT_LOCATIONCHANGE` / `EVENT_OBJECT_NAMECHANGE`）替代或补充轮询。
- 微信最小化/关闭时隐藏覆盖层。

> 注意：窗口位置变化与聊天切换是**两套独立刷新机制**，不得让 `LocationChange` 承担 `ChatName` 变化检测（见 6.2 模块拆分）。

> **Spike-01 实测（2026-09-28）**：最大化后主窗口 `GetWindowRect` 为 `(1912,-8,3848,1048)`，含 8px 不可见边框；其渲染子窗口为 `(1920,0,3840,1040)`。**覆盖层必须对齐渲染子窗口矩形，或改用 `DwmGetWindowAttribute(DWMWA_EXTENDED_FRAME_BOUNDS)`**，否则无法满足"位置误差 < 2px"的验收要求。

#### 6.3.4 DPI 处理（修订：先定 Awareness 再实测）
1. 首先确定本进程的 DPI Awareness（Unaware / System / Per-Monitor / Per-Monitor V2）。
2. 在 Awareness 未确定前，**不预设** `GetDpiForWindow` / `PhysicalToLogicalPoint` 等具体转换 API。
3. 按 DPI 矩阵（见 7.3）实测后再确定坐标转换方案，避免"微信位置正确、覆盖层偏移"。

#### 6.3.5 聊天对象识别（视觉 / OCR 通道，见 7.7）
> 2026-09-28 实测：窗口标题通道与 UI Automation 通道均不可用（见 7.6）；**视觉 / OCR 通道经验证成立**（见 7.7）。
> 实现要点：对渲染子窗口客户区按 96 DPI 基准偏移区域裁剪并**按 `dpi/96` 归一化**（区域 × `dpi/96`；随后先缩回 96 DPI 基准尺寸、再按整数倍数放大）→ 三路预处理变体分别 OCR → 取并集 → 按全串包含匹配判定风险。

```csharp
// 伪代码：IChatTracker 的接口形态（视觉识别的实现要点见 7.7）
IntPtr chatWnd = /* 由 WindowTracker 定位的微信聊天窗口 */;
string? chatName = tracker.TryGetChatName(chatWnd); // 失败返回 null，不得回退为"私聊"

var ctx = new ChatContext {
    Hwnd = chatWnd,
    Rect = rect,
    ChatName = chatName,
    Identity = chatName is null ? ChatIdentityState.Unknown : ChatIdentityState.Known
};
```

> **视觉识别的实现约束**（来自 7.7 实测）：
> - 三路预处理变体（原色 / 灰度对比拉伸 / 大津二值化）**并集**是必要条件，单路会漏报（`BUG`→`BIJG`）；
> - 匹配必须是**全串包含**，不得"仅比对汉字"（会因共用前缀误报）；
> - 识别结果为空或失败时**不得静默放过**，须走 FR-09 失败策略；
> - 裁剪区与放大倍数须按 `dpi/96` 归一化，保持 `等效放大 = ocrScale × dpi/96` 恒定；实现上先把物理裁剪图缩回 96 DPI 基准尺寸、再按整数 `ocrScale` 放大（避免 150% 下非整数最近邻插值畸变，见 12.4.3）；
> - `ChatContext` **不提供 `IsGroup`**，风险判定只依据 `ChatName` 全串包含匹配。

### 7.6 Spike-01 实测记录（2026-09-28，三轮）

**实测环境**：Windows 10.0.19045；微信 4.x（进程名 `Weixin.exe`，多进程：`Weixin` × 3 + `WeChatAppEx`）；双显示器（主屏 1920×1080 位于 (0,0)，副屏自 x=1920 起），均 100% DPI；侦察工具以 Per-Monitor V2 感知运行。三轮实测：第一轮窗口滚动/最大化/最小化/前台切换（15:04:56–15:06:03，间隔 300ms）、第二轮 ②③④ 会话切换专项复测（15:56:26–15:57:25）、第三轮 UI Automation 通道验证（16:28:54–16:30:46）。

**微信 4.x 窗口清单（本机实测节选）**：

| 类别 | 类名 | 标题 | 说明 |
|------|------|------|------|
| 主窗口 | `Qt51514QWindowIcon` | `微信` | 唯一主界面窗口句柄 `0x0001089C`；标题固定，不随聊天对象变化 |
| 主窗口唯一子窗口 | `MMUIRenderSubWindowHW` | `MMUIRenderSubWindowHW` | Qt 统一渲染面，标题即类名，不含会话信息；矩形紧贴主窗口客户区 |
| 临时窗口 | `Qt51514QWindowToolSaveBits` | `Weixin` | 514×514，出现后又消失，**不可误判为聊天窗口** |
| 托盘消息窗 | `Qt51514WxTrayIconMessageWindowClass` | `WxTrayIconMessageWindow` | 常隐藏 |
| 小程序/内嵌页 | `Chrome_WidgetWin_0`、`Chrome_RenderWidgetHostHWND` | — | 属 `WeChatAppEx` 进程 |
| 系统辅助（需过滤） | `Base_PowerMessageWindow`、`IME`、`MSCTFIME UI`、`Chrome_SystemMessageWindow`、`DisplayICC_SystemMessageWindow` | — | 无业务价值 |

单次快照共枚举到微信相关窗口 20 个，其中真正有业务意义的仅主窗口与其渲染子窗口。

**关键结论（附原始证据）**：

1. **主窗口标题不携带聊天对象名（决定性）**。整段监视中主窗口 `WindowText` 始终为 `"微信"`，未出现任何 `WindowText` 变更，窗口内亦不存在"会话标题"子窗口。
   → `GetWindowText` 识别聊天对象**在本版本不成立**。（第二轮 ②③④ 专项复测再次确认，见下方"②③④ 复测结论"。）
2. **微信 4.x 为 Qt 自绘架构**：主窗口仅 1 个渲染子窗口，会话列表 / 消息区 / 输入框均无独立 HWND。
   → "通过控件树找会话标题或群成员列表"的旧思路同样不适用。

### 7.7 Spike-05 实测记录：视觉 / OCR 识别通道（2026-09-28）

**完整设计与证据**：《Spike-05验证设计.md》第 12 节。**证据目录**：`WeChatWindowInspector/logs/spike05/`（12 组样本，含 DPI 125% 2 组）

**复现命令**：

```text
WeChatWindowInspector --ocr --ocr-dir logs\spike05 --ocr-region 300,33,580,30 --ocr-region-dpi96 --ocr-scale 5 ^
  --names "培立优BUG,培立优杨潇,徐二狗,24级3班,培立优办公室群"
```

**方案**：对渲染子窗口客户区按 96 DPI 基准偏移区域 `(300,33,580,30)` **经 `dpi/96` 归一化后**裁剪（`--ocr-region-dpi96`：区域 × `dpi/96`；随后先把裁剪图缩回 96 DPI 基准尺寸、再按整数 `ocrScale` 放大），经**三路预处理变体**（`raw` 原色 / `stretch` 灰度对比拉伸 / `otsu` 大津二值化）分别 OCR，结果取**并集**，再与风险名单做**全串包含匹配**。

**判据结论**：

| 判据 | 结果 | 说明 |
|------|------|------|
| G0 截图可行 | ✅ 通过 | `PrintWindow(PW_RENDERFULLCONTENT)` 可稳定捕获 Qt 自绘内容 |
| G1 几何稳定 | ✅ 通过 | 同一裁剪区在 880×637、1920×1040、1100×796 三种尺寸、7 个会话下均裁出完整标题；标题**左锚定**于客户区 x≈311，右边缘极差 2px；125% 下按 `dpi/96` 缩放后同样成立 |
| G2 OCR 可用 | ✅ 通过 | 12 个样本（含 125%）"识别文本包含配置会话名即提醒"判定口径与严格口径**均 12/12 = 100%**，71ms/次（3 路变体） |
| G3 群/私可分 | ❌ 不通过 | 无稳定视觉差异，`(N)` 成员数 / 表情 / 备注均不可作判据 |

**识别率的关键事实（必须写入实现假设）**：

1. **单路识别不可靠**。`raw` 会把拉丁字母 `BUG` 误识为 `BIJG`（漏报风险）；`otsu` 对短会话名（如 `徐二狗`）返回空。**只有三路并集才能在 12 个样本上全部正确**。
2. **必须全串包含匹配**。"仅保留汉字再比对"会误报 —— `培立优办公室群`、`培立优杨潇` 都会因共用前缀 `培立优` 而错误触发 `培立优BUG` 规则。
3. **G2 的口径**：按 sidecar `scene` 字段严格比对，修正标注前为 8/12；差异全部源于该字段混入了场景描述前缀（`最大化…`、`小窗…`、`DPI125…`）。已把这 4 个 sidecar 的 `scene` 修正为纯会话名、场景描述移入 `note` 字段，修正后严格口径为 **12/12**。这是一次**标注修正**，OCR 侧识别结果前后未变。
4. **裁剪区与放大倍数必须同时按 `dpi/96` 归一化**。固定物理像素偏移在 125% 下**完全失效**（OCR 输出为空或噪字）；且只缩放裁剪区不缩放放大倍数也会失败（等效放大 `5×1.25=6.25` 是较差档位）。两条规则必须同时满足：区域 × `dpi/96`、放大倍数 ÷ `dpi/96`，保持 **`等效放大 = ocrScale × dpi/96` 恒定**。100% 样本结果与归一化前**逐字节一致**（回归无损）。
   **150% 补测修正（2026-09-28）**：直接按 `ocrScale ÷ (dpi/96)` 放大在 150% 下倍数为非整数 `3.33`，`otsu` 变体的最近邻插值会畸变字形（`优`→`fi`）导致**漏报**。改为**先把物理裁剪图缩回 96 DPI 基准尺寸、再按整数 `ocrScale` 放大**后，150% 连续 3 次稳定命中（详见 Spike-05 第 12.4.3 节）。

### 7.8 OCR 识别准确度提升（Phase C：变体改造 + 引擎对比，2026-09-30）

**目标**：把 OCR 预处理变体轴由 3 路（`raw` / `stretch` / `otsu`）扩到 **7 路**（新增 `fixed-140` / `fixed-180` / `invert` / `invert+stretch`），降低**字符级**识别错误（痛点字：`课`、`常`、`亮`、`素`）。

**结论：7 路变体改造否决（Windows 引擎下无效）；换引擎（PaddleOCR）可彻底解决准确度，但需先定性能与体积策略**。完整方案与结果见《Spike-05验证设计.md》**第 13 节**（13.8.2 结果 / 13.8.3 决策）。

- **否决依据**：四场景（浅色 100% / 浅色 125% / 深色 100% / 深色 125%）并集命中率 **61.5% / 83.3% / 53.8% / 33.3%**，均远低于 13.7 的 95% 门槛；`invert` / `invert+stretch` 与 `raw` / `stretch` **实测逐格完全相同**（`Windows.Media.Ocr` 已内部做极性归一化）；`otsu` / `fixed-140` / `fixed-180` 全线垫底。
- **维持不改**：生产仍为 `raw` + `stretch` 并集判定；`ocrScale` 甜区为 **2x~3x**（1x 完全失效、4x 及以上淘汰）——**均无需改代码**。
- **真实瓶颈**：引擎对复杂汉字的识别能力，表现为两类错误 —— **丢字**（`课`/`素`/`董`）与**形近替换**（`常→堂`、`立→丷`、`教→敖`、`优→忧`）；已排除长名截断与裁剪区偏移两个假设。
- **采样口径变更**：由"场景驱动"改为"**会话名集合驱动 + 场景叠加**"，以**字符**为统计单元（字符级准确率 + 错字清单），整串命中率仅作辅助。
- **追加结论（跨 Scale 并集）**：单一 Scale 无法覆盖全部样本（同一字在不同 Scale 下时对时错），改取 2x+3x+4x × 全部变体的并集，四场景平均命中率 65.7% → **72.0%**（dark125 +16.7pt、light125 +8.4pt），成本 178~183 ms/样本，仍在 FR-05 的 200 ms 预算内；**但仍未达 95% 门槛**，优先级下调。
- **追加结论（引擎对比，2026-09-30）**：以新增的 `--bench-engine windows|paddle` 在同一流水线上只替换识别引擎 —— **PaddleOCR PP-OCRv5 在 4 个场景 × 3 个 Scale × 7 路变体上全部 100.0% 命中 / 100.0% 字准**（错字清单为空，`董天娇`/`培立优陈素冉`/`君逸左岸6号楼7号楼交流群` 等失败样本全部解决）；Windows.Media.Ocr 最高仅 91.7%。**代价**：单次约 610~780 ms（**超 FR-05 的 200 ms 预算 3 倍以上**）与**产物 498 MB**（Paddle 原生 267 MB + OpenCV 127 MB）。PaddleOCR 下**变体轴与 Scale 轴均无区分度**，单路 `raw` @ 2x 即可。**是否换引擎待决策**（须先定性能预算与打包策略），见 Spike-05 13.8.2 ⑨ / 13.8.3 决策 10。

**采集与工具（保留备查）**：

- **采集规模 50 帧**：按主题/缩放分四个目录 `logs\spike05-phaseC-{light100,light125,dark100,dark125}`，覆盖 13 个真实会话名（含目标错字 `素`/`亮`/`课`/`常` 与 2 个超长名），每名 1 帧（主题工具不识别、须靠目录区分；屏幕缩放由 sidecar 的 `dpi`/`scalePercent` 自动记录）；
- **工具**：`WeChatWindowInspector --ocr-bench`（Phase C），支持 7 路变体扫描、Scale / 阈值轴、`--bench-variants` 消融、**`--bench-engine windows|paddle` 引擎切换**、跨 Scale 并集口径、字符级准确率与错字清单 CSV。

**下一步**：**决定是否切换到 PaddleOCR 引擎** —— 需先定 FR-05 的性能预算（放宽到 ~700 ms / 改为标题变化触发 / 多线程）与 498 MB 的打包策略，通过后识别即可退化为**单路 `raw` @ 2x**；详见 Spike-05 13.8.3 决策 10。分辨率方向已验毕（甜区 2x~3x）；跨 Scale 并集仅 +6.3pt、不足以达标，优先级下调。

### 9.3 性能测试结果（2026-09-29）

**被测版本**：最终选型 —— 框架依赖单文件 `WeChatSendGuard.exe`（24.5MB）。
**被测环境**：Windows 10 专业版 22H2（Build 19045），8 逻辑核，双显示器 1920×1080 @96 DPI；微信 4.1.13.65（渲染区位于第二显示器 `2957,400,3830,1034`）。
**方法**：脚本启动被测程序 → 预热 25s → 用 `Get-Counter '\Process(WeChatSendGuard)\% Processor Time'`（与任务管理器同源的 PDH 计数器）以 1s 间隔连续采样 60 次；每阶段前后读取一次工作集。阶段 B 前用 `AttachThreadInput + SetForegroundWindow` 把微信置前，并以"日志中是否新增识别记录"交叉验证 OCR 是否真的在跑。

> **口径说明**：PDH `\Process\% Processor Time` 以**单个逻辑核**为 100%；任务管理器的进程 CPU 列按**整机**（= 逻辑核数）归一化。下表同时给出两种口径（整机口径 = 核口径 ÷ 8）。

| 指标 | 5.1 目标 | 阶段 A：微信非前台（OCR 跳过） | 阶段 B：微信前台（OCR 运行） | 判定 |
|------|----------|------------------------------|----------------------------|------|
| CPU（核口径 avg） | — | 0.34% | 14.64% | — |
| CPU（整机口径 avg） | < 1% | 0.04% | **1.83%** | ❌ **超标** |
| CPU（核口径 max / 整机口径） | < 5% | 3.09% / 0.39% | 32.28% / **4.04%** | ✅ 刚达标 |
| 私有工作集（≈ 任务管理器"内存"列） | < 100MB | 34.3MB | 53~56MB | ✅ |
| 工作集 `WorkingSet64`（含共享/映射的运行时页） | — | 130.0MB | 150.9MB | 参考项 |
| 60s 内工作集变化 | 无持续增长 | −0.6MB | −4.7MB | ✅ |

**识别正确性交叉验证**：阶段中出现识别记录 `识别参数：dpi=96（100%），裁剪区=300,33,580x30，缩回基准 573x30，放大=5x` 与 `未命中：识别文本 24 级 3 班（89）` —— 说明框架依赖发布版下 **WinRT OCR 正常**，且"识别成功但未命中名单"时不显示覆盖层（符合预期）。

**结论**：

1. **CPU 峰值达标，CPU 平均未达标**：OCR 运行期间整机口径平均 **1.83%**，超过 5.1 的 "< 1%"。原因是默认 `ocrIntervalMs = 500ms` 即每秒 2 次 OCR，单次约 70~100ms（约 0.6 个逻辑核的瞬时占用）。
   **可执行的收敛手段**：把 `ocrIntervalMs` 调到 `1000`（每秒 1 次）即可让平均值落到约 0.9%；代价是"切换会话"后状态提交最长再晚约 0.5s（叠加去抖后总延迟 ≤ 约 1.5s，对"防误发"场景可接受）。**本版未改默认值**（默认保守取 500ms 以获得更快提醒），按 5.1 口径如实记为未达标。
2. **内存达标**（按任务管理器口径的私有工作集）：空转 34.3MB、OCR 运行 53~56MB，均 < 100MB；采样窗口内**无持续增长**。注意原始 `WorkingSet64` 约 130~151MB，其中包含与系统共享、按文件映射的运行时页，不是本进程的私有占用。
3. **未执行项**：5.1 要求的"连续 30 分钟采样"与 5/9.1 的"连续运行 8 小时无崩溃"未执行（本次为 2×60s 采样 + 多次长跑侧面验证）；**位置同步延迟 95% < 100ms** 未用高速录屏抽样，仅可论证其理论上限由 100ms 轮询 + 变化才 `SetWindowPos` 决定。以上登记为遗留。

#### 9.3.1 附：装包方式对内存的影响（选型依据）

同一份代码、同一台机器，"空转"指微信非前台（OCR 跳过）。压测发现**单文件压缩**是内存膨胀的主因：

| 装包方式 | 状态 | 产物体积 | 工作集 | 私有工作集 |
|----------|------|---------|--------|-----------|
| 自包含单文件 + `EnableCompressionInSingleFile` | 空转 | 78MB | 291.6MB | **140.3MB** |
| 自包含单文件 + `EnableCompressionInSingleFile` | OCR 运行 | 78MB | 322.1MB | — |
| 自包含（散开文件夹，不压缩） | 空转 | 多文件 | 128.9MB | 33.8MB |
| 自包含单文件（不压缩） | OCR 运行 | 189.2MB | 163.2MB | 52.8MB |
| **框架依赖单文件（最终选型）** | 空转 | 24.5MB | 130.0MB | 34.3MB |
| **框架依赖单文件（最终选型）** | OCR 运行 | 24.5MB | 150.9MB | 53~56MB |

同样在"空转"下对比：压缩版私有工作集 **140.3MB**、不压缩版 **33.8MB** —— 压缩会让运行时把解压后的全部托管程序集常驻**私有**内存，直接击穿 100MB 目标；而"自包含 vs 框架依赖"本身差异很小（33.8MB vs 34.3MB）。

**最终决策**：采用**框架依赖单文件**（24.5MB，私有工作集最小之一，且保留"单文件双击即用"）；代价是目标机需预装 .NET 10 桌面运行时。若需免预装，备选自包含发布，但**必须关掉 `EnableCompressionInSingleFile`**（否则内存不达标）。

详见 `WeChatSendGuard.App/Properties/PublishProfiles/win-x64.pubxml` 与 `README.md` 第 8 节。

| **核心识别方案（标题=聊天名）不成立** | **已发生（微信 4.x 实测确认）** | 高 | 已改写 FR-01；识别不再依赖窗口标题 |
| ~~**自动识别路径整体不可用（窗口层 + UI Automation 均无信号）**~~ | **已缓解（2026-09-28）** | 中 | 该风险已发生但已被 Spike-05 的视觉 / OCR 通道绕开（见 7.7）；残留风险转为"识别率为弱信号"：**DPI / 主题 / UI 版本变化可能导致识别率下降**，须落实 FR-09 失败策略与"识别失败不静默放过" |

## 11. 验收标准

### 11.1 正向验收
1. 覆盖层能准确跟随微信聊天窗口，位置误差 < 2px，延迟满足 5.1 口径（95% < 100ms）。
2. 当聊天对象命中配置名单时，显示红色边框和风险标签。
3. 支持至少 20 条名单配置，且支持精确/包含/正则三种匹配模式。
4. 配置保存后立即生效。
5. 提供托盘图标和全局热键（默认 `Ctrl+Alt+G`）控制开关。**（修订：全局热键经确认不纳入 v1.0，易与其他软件冲突；改由托盘菜单"启用提醒"承担，见 8.2 第 2 周）**
6. 连续运行 8 小时无崩溃，性能满足第 5 节指标。
7. 不注入微信进程，不读取聊天内容，不联网。

### 11.2 负向验收（新增，必须全部通过）
1. 微信最小化 / 关闭 / 崩溃时，覆盖层均不存在。
2. 微信失去前台（如切到 Chrome）时，覆盖层不显示。
3. 非风险聊天不显示任何提醒。
4. 覆盖层完全鼠标穿透、不抢焦点、不影响键盘；Alt+Tab、Win+D 正常。
5. 窗口移动、最大化、DPI 变化时无残影、无偏移。
6. **识别失败时判定为"无法识别"，绝不给用户"安全/私聊"的错误安全感。**

### 11.3 实测验收结论（2026-09-29）

| 条目 | 结论 | 依据/偏差 |
|------|------|----------|
| 11.1-1 跟随与误差 | ✅ 位置误差 0px（覆盖层 HWND 与渲染区逐像素相等） | Spike-05 12.6 / 12.7。**延迟未抽样**，仅论证理论上限（100ms 轮询） |
| 11.1-2 命中时显示红框/标签 | ✅ | 12.7 N0（红框与渲染区逐像素相等） |
| 11.1-3 ≥20 条名单 + 三种匹配模式 | ✅（结构支持，未做 20 条专项加载测试） | 9.3 未覆盖、如实登记 |
| 11.1-4 保存后立即生效 | ✅ | 配置界面"保存并应用"写回并热重载 |
| 11.1-5 托盘图标 + 全局热键 | ⚠️ 托盘 ✅；**全局热键已按修订取消** | 见 11.1-5 修订说明 |
| 11.1-6 8 小时无崩溃 + 性能达标 | ⚠️ **部分**：长稳未执行；CPU 平均超标（1.83% > 1%）、峰值达标、内存达标 | 详见 9.3 |
| 11.1-7 不注入 / 不读聊天 / 不联网 | ✅ | 代码审计（9.2.1） |
| 11.2-1 最小化/关闭/崩溃不残留 | ✅（"崩溃"以 `SW_HIDE` 近似 + 代码审计） | 9.2.1 |
| 11.2-2 失去前台不显示 | ✅ | 9.2.1 N2 |
| 11.2-3 非风险聊天不显示 | ✅ | 9.3 实测：识别到 `24 级 3 班（89）` 未命中名单 → 不显示 |
| 11.2-4 穿透/不抢焦点/不影响键盘、Alt+Tab、Win+D | ✅（Win+D 实测；**Alt+Tab 未单独实测**，N2 覆盖其最终效果） | 12.7 N6 / N7 |
| 11.2-5 移动/最大化/DPI 无残影偏移 | ✅（**跨屏混合 DPI 未实测**） | 12.7 N4 / N5、12.5 #9 |
| 11.2-6 识别失败不给错误安全感 | ✅ | 9.2.1；`CanRecognize` 不满足时清空上下文并隐藏覆盖层 |

**总结**：负向验收 **6/6 通过**；正向验收 7 项中 5 项通过、2 项部分（全局热键已按修订取消、8 小时长稳与 CPU 平均未达标）。未达标/未执行项与建议已登记在 9.3 结论与 `Spike-05验证设计.md` 12.5。

## 12. 版本演进规划（修订）

明确各版本边界，避免 v1 架构为未来能力（如键盘钩子）提前复杂化：

| 版本 | 范围 | 关键新增 |
|------|------|----------|
| **v1.0** | 会话级风险提醒 | 手动名单、透明覆盖层、状态机、失败策略；**当前会话名由视觉 / OCR 通道识别（Spike-05 验证成立，见 7.7）**，按**全串包含匹配**判定风险 |
| **v1.5** | 自动识别风险聊天 | ~~通过 UI Automation 判断群聊/风险聊天~~（**该通道已实测排除，见 7.6**）；视觉通道已提前到 v1.0 落地，v1.5 转为提升识别鲁棒性（DPI 自适应、多主题、模板重采集） |
| **v1.6** | 群/私类型判别（候选） | 视觉通道无法提供（G3 不通过）；如需该能力须另寻通道，或改为**用户在名单中显式声明类型** |
| **v2.0** | 输入内容风险检测 | 敏感词提醒（开始读取用户输入，需重新评估隐私与安全边界） |
| **v3.0** | 发送动作拦截 | 发送前二次确认（需键盘/发送事件监听，风险与复杂度显著上升） |

> v2.0 及以后已从"Window Overlay"演变为"输入安全防错系统"，其架构约束与合规要求需单独评审。
