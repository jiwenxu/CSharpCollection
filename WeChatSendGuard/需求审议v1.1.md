这份 Spike-01 实测结果把我上一轮认为最大的风险点基本**坐实了，而且结论比预期更明确**：

> **微信 4.x 的“当前聊天对象识别”不能再沿着 Win32 窗口属性 / UI Automation 这条路线继续挖。**

你已经完成了决定性验证：主窗口标题固定为“微信”，会话切换没有任何窗口属性变化；UIA 也只有单一渲染 Pane，没有会话级节点。这个结论足够支撑对原需求文档做一次架构级调整。

我建议现在**不要急着找下一个“神奇 API”继续撞 UIA**，而是先重新定义 v1.0 的可交付目标。

## 1. Spike-01 的结论是成立的

你这次实际上验证了三条独立通道：

```text
Win32 WindowText
        ↓
       失败

Win32 窗口属性变化
        ↓
       失败

UI Automation
        ↓
       失败
```

而且第二轮最有价值：

> 7 次实际会话切换，17 个窗口完全一致，0 条属性变化。

这已经不是“当前代码没找到”的级别，而是：

> **微信 4.x 当前会话切换没有暴露在你所监控的 Win32 窗口状态中。**

第三轮又把 UIA 路线排除了：

> `MMUIRenderSubWindowHW` 是一个零子节点 Pane，不支持 UIA 模式。

因此你文档里原来的：

> “通过 GetWindowText 或 UI Automation 获取当前激活的微信聊天窗口标题”

应该正式判定为**废弃方案**，而不是继续保留为 MVP 设计。

现在这个 FR 已经被实测否定。

```text
    ↓
```

# 3. v1.0 现在有三个方向

这里要把产品需求和技术实现分开。

你真正需要的是：

```text
当前是不是用户配置的高风险聊天？
```

至于怎么获得这个状态，可以有多个候选通道：

```text
A. 窗口属性
B. UI Automation
C. 图像/OCR
D. 微信内部数据
E. 用户主动标记
F. 其他外部可观测状态
```

你已经把：

```text
A ❌
B ❌
```

排除了。

因此现在真正值得研究的是：

```text
C / D / E
```

---

# 4. 我反而建议你暂时不要碰 D：微信内部数据

因为你的原始产品边界非常明确：

> 不注入微信进程、不修改微信文件、不读取聊天内容、不联网。

如果走微信内部数据，例如数据库、进程内存、内部接口等，整个安全模型都会发生变化。

而且你的产品真正需要的只是：

> “当前是不是某个风险聊天”

并不需要：

> “读取微信内部数据”。

所以我暂时不会建议为了救 FR-05 就把架构推进到进程注入、内存读取之类的方向。

---

# 5. 真正值得验证的是 C：视觉识别

因为你已经证明：

```text
程序无法从微信的语义层得到：

ChatName = xxx
```

但用户本人能够看到：

```text
微信窗口
┌───────────────────────────┐
│       当前聊天名称         │
│                           │
│       消息区域             │
│                           │
│                           │
│       输入框               │
└───────────────────────────┘
```

这意味着：

> **信息虽然没有暴露给 API，但信息实际上被渲染到了屏幕。**

这时候 OCR 就成为一个非常自然的第三条路线。

# 6. OCR 不应该一上来就“识别整个微信”

这是这里最容易走歪的地方。

不要：

```text
截图整个微信
 ↓
OCR 全部文字
 ↓
寻找群名
```

这样成本和误识别都会比较高。

应该先利用你已经得到的稳定信息：

```text
微信主窗口
    ↓
MMUIRenderSubWindowHW
    ↓
得到渲染区域 Rect
```

然后只截取：

> **当前聊天标题所在区域**

例如：

```text
┌──────────────────────────────────────────┐
│ 左侧会话列表 │     当前聊天名称          │ ← OCR
│              │──────────────────────────│
│              │                          │
│              │                          │
│              │                          │
└──────────────────────────────────────────┘
```

如果微信 4.x 的布局稳定，那么 OCR 的工作量其实会非常小。

---

# 7. 但这里有一个比 OCR 更重要的问题：先验证“标题区域是否稳定”

所以我建议下一步不要直接开发 OCR。

先做：

## Spike-05：聊天标题视觉区域验证

只做一件事情：

> **确定微信 4.x 当前聊天名称在屏幕上的位置和变化规律。**

测试：

```text
私聊 A
私聊 B
群聊 A
群聊 B
群聊 A → 群聊 B
群聊 → 私聊
```

每次：

```text
截图
记录窗口 Rect
记录标题区域坐标
```

然后回答：

### ① 标题是否始终在固定区域？

例如：

```text
x = window.left + 600
y = window.top + 20
```

### ② 标题区域是否会因为窗口大小改变而变化？

### ③ 标题区域是否因为 DPI 改变而变化？

### ④ 群聊和私聊标题视觉上有没有差异？

### ⑤ 群聊标题是不是一定包含某种稳定视觉特征？

如果这些成立，OCR 路线就值得继续。

# 9. 还有一个非常值得考虑的产品调整：用户主动标记

假设 OCR 最终也不够稳定。

其实你的产品仍然可以成立。

可以把 v1 改成：

```text

        ↓

```

问题马上来了：

如果没有 ChatName，就需要一个稳定 fingerprint。

例如未来可以探索：

```text

+

+
```


# 10. 但是要特别注意一个问题：不要把截图 Hash 当成聊天 ID

例如：

```text
群聊 A
截图 hash = XXXXX
```

这只能说明：

> 当前视觉状态类似。

不能直接认为：

> 这是群聊 A 的真实唯一身份。

因为：

* 主题可能改变
* 字体可能改变
* DPI 可能改变
* 窗口尺寸可能改变
* 群名可能改变
* 微信 UI 版本可能改变

所以如果最终走视觉路线，我会把它定义为：

```text
VisualChatFingerprint
```

而不是：

```text
ChatId
```

这个边界很重要。

# 12. 这样 FR-05 可以改成真正稳定的需求

我建议写成：

> ### FR-05 当前聊天风险识别
>
> 系统应尝试确定当前微信聊天是否属于用户配置的高风险聊天。
>
> 识别机制由 `IChatIdentityProvider` 抽象，具体实现不作为 FR-05 的固定要求。

这比现在：

强得多。

# 14. Spike-01 还有一个很有价值的结论：Overlay 对齐对象已经发生变化

你发现：

```text
主窗口:
(1912,-8,3848,1048)

Render:
(1920,0,3840,1040)
```

这个非常重要。

原需求写的是：

> 获取聊天窗口屏幕坐标与尺寸。

现在应该把这个定义进一步明确：

> **Overlay 的业务对齐目标不是 Win32 顶层窗口 Rect，而是 `MMUIRenderSubWindowHW` 的客户渲染区域 Rect。**

这实际上是一个很好的 Spike-01 输出。

# 15. 因此 FR-01/FR-02 我建议这样改

### FR-01

原：

> 枚举系统窗口，定位微信主窗口及当前聊天窗口。

建议改：

> 枚举系统窗口，定位微信 4.x 主窗口及其渲染子窗口；根据进程、类名白名单及窗口层级关系排除辅助窗口。

### FR-02

原：

> 实时获取聊天窗口的屏幕坐标与尺寸。

建议改：

> 获取微信渲染子窗口 `MMUIRenderSubWindowHW` 的屏幕坐标与尺寸，作为 Overlay 的主要对齐区域；必要时结合 DWM 扩展边界进行校验。

这样和你的实测结果完全一致。

## 最后一个关键判断

你这次实测实际上把项目从：

> **“Win32 窗口辅助工具”**

推向了：

> **“基于 Windows 外部可观测信息的微信防错工具”**

这是一个很重要的架构变化。

因此下一版需求文档最好不要再把：

```text

```

写死。

应该把**“识别通道”降为实现细节，把“风险聊天识别”提升为产品需求**。
